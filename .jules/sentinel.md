## 2023-10-27 - IDOR in Update Endpoints
**Vulnerability:** Insecure Direct Object Reference (IDOR) / Missing Ownership Check in the `PUT /duvidas/{id}` endpoint. An authenticated user could update any other user's doubt because the endpoint did not check if the current user was the owner of the resource being updated.
**Learning:** Sometimes ownership checks are correctly implemented in destructive endpoints like `DELETE` but missed in `PUT` / `PATCH` endpoints. We must enforce ownership checks on all endpoints that modify a resource, retrieving the existing resource before applying the update.
**Prevention:** Always retrieve the entity from the database and verify the `current_user` matches the entity owner (or has the appropriate admin/monitor roles) *before* processing the update payload.

## 2023-10-27 - IDOR and Mass Assignment in Messages Endpoint
**Vulnerability:** Insecure Direct Object Reference (IDOR) and Mass Assignment vulnerabilities in the `PUT /mensagens/{id}` and `DELETE /mensagens/{id}` endpoints. Any user involved in a message thread could edit or delete the message, not just the sender. Additionally, users could arbitrarily change the `remetente` (sender), `destinatario` (recipient), or `horario` fields because `mensagem_update.model_dump().items()` was being used blindly.
**Learning:** Checking for participation (e.g., `user in (sender, receiver)`) is insufficient for destructive or mutating endpoints like edit and delete; strict ownership verification is required. Blindly updating all fields from Pydantic models leads to Mass Assignment vulnerabilities.
**Prevention:** Always ensure the `current_user` matches the strict owner (`remetente`) of a resource before modifying or deleting it. Never iterate through `.model_dump()` to blindly construct MongoDB updates for endpoints where some fields should be immutable. Explicitly extract and update only the permitted fields.
