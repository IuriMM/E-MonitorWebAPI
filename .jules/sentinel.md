## 2023-10-27 - IDOR in Update Endpoints
**Vulnerability:** Insecure Direct Object Reference (IDOR) / Missing Ownership Check in the `PUT /duvidas/{id}` endpoint. An authenticated user could update any other user's doubt because the endpoint did not check if the current user was the owner of the resource being updated.
**Learning:** Sometimes ownership checks are correctly implemented in destructive endpoints like `DELETE` but missed in `PUT` / `PATCH` endpoints. We must enforce ownership checks on all endpoints that modify a resource, retrieving the existing resource before applying the update.
**Prevention:** Always retrieve the entity from the database and verify the `current_user` matches the entity owner (or has the appropriate admin/monitor roles) *before* processing the update payload.

## 2026-09-13 - Authorization Bypass and Forgery in Messages
**Vulnerability:** Insecure Direct Object Reference (IDOR) and Missing Field Filtering in `PUT /mensagens/{id}` and `DELETE /mensagens/{id}`. An authenticated user participating in a conversation as a recipient could edit or delete the sender's messages. In addition, the PUT endpoint allowed users to forge the `remetente` (sender), `destinatario` (recipient), and `horario` fields because they were blindly accepted from the payload.
**Learning:** Authorization checks involving participants must carefully delineate permissions. Just being a participant does not grant write access to resources owned by another participant. Also, never blind-merge update payloads into the database without stripping protected fields.
**Prevention:** Ensure ownership checks strictly match the entity's owner field (e.g. `remetente`) before update/delete operations, and always sanitize update payloads to drop fields that should only be controlled by the server or created at insertion time.
