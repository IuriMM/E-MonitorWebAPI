## 2023-10-27 - IDOR in Update Endpoints
**Vulnerability:** Insecure Direct Object Reference (IDOR) / Missing Ownership Check in the `PUT /duvidas/{id}` endpoint. An authenticated user could update any other user's doubt because the endpoint did not check if the current user was the owner of the resource being updated.
**Learning:** Sometimes ownership checks are correctly implemented in destructive endpoints like `DELETE` but missed in `PUT` / `PATCH` endpoints. We must enforce ownership checks on all endpoints that modify a resource, retrieving the existing resource before applying the update.
**Prevention:** Always retrieve the entity from the database and verify the `current_user` matches the entity owner (or has the appropriate admin/monitor roles) *before* processing the update payload.

## 2026-09-22 - IDOR and Mass Assignment in Messages
**Vulnerability:** IDOR in `PUT` and `DELETE` /mensagens/{id} and Mass Assignment in `MensagemUpdate`. Any participant of a conversation could edit or delete the message, not just the sender. Additionally, the `MensagemUpdate` model allowed the sender to update immutable fields like `destinatario`, `remetente`, and `horario`.
**Learning:** Checking for "participation" is not sufficient for authorization in modification/deletion endpoints; the actual owner (sender) must be verified. Pydantic models for update operations must explicitly exclude immutable fields to prevent mass assignment vulnerabilities, which could otherwise allow users to spoof the sender or recipient of a message.
**Prevention:** Always verify that the `current_user` is the specific owner/author of the resource, rather than just a participant, for endpoints that perform destructive or modify actions. Ensure that Update models (`*Update`) strictly define only the fields that are allowed to be modified by the user.
