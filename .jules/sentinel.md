## 2023-10-27 - IDOR in Update Endpoints
**Vulnerability:** Insecure Direct Object Reference (IDOR) / Missing Ownership Check in the `PUT /duvidas/{id}` endpoint. An authenticated user could update any other user's doubt because the endpoint did not check if the current user was the owner of the resource being updated.
**Learning:** Sometimes ownership checks are correctly implemented in destructive endpoints like `DELETE` but missed in `PUT` / `PATCH` endpoints. We must enforce ownership checks on all endpoints that modify a resource, retrieving the existing resource before applying the update.
**Prevention:** Always retrieve the entity from the database and verify the `current_user` matches the entity owner (or has the appropriate admin/monitor roles) *before* processing the update payload.

## 2024-05-24 - Broken Access Control and Mass Assignment in Mensagens
**Vulnerability:** Authorization bypass and mass assignment spoofing in message updates and deletions. Any conversation participant could edit or delete messages sent by the other person. Additionally, the `MensagemUpdate` model allowed malicious users to update the `destinatario` and `remetente` fields to spoof message authorship or recipients.
**Learning:** Checking if a user "participates" in a conversation is insufficient for destructive or mutating operations. In a messaging system, authorization logic must specifically verify the user is the explicit author of the specific message. Pydantic models for update operations must also explicitly omit fields that should remain immutable after creation.
**Prevention:** Strictly enforce that `current_user` matches the original author for resource mutation (e.g., `current_user["nome"] == mensagem["remetente"]`). Ensure update schemas omit fields like sender, recipient, or identifiers that should be write-once to prevent mass assignment vulnerabilities.
